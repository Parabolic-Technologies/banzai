This brief hands Claude Code a staged plan for banzai 2.8–2.9: stop losing runs at verification, let people edit plans without hand-computed digests, remove install and model-config friction, and make Claude the default reviewer. Work one package at a time, and stop at every ADR and gate for the owner's decision.

## How to work with this brief

The brief is self-contained: it names the files, the evidence and the expected result for every work package. Where the code has moved since commit `0145686` (banzai 2.7.4, 23 October), trust the code and say what differs.

1. **Read first.** Root `AGENTS.md`, `PROJECT_MANIFEST.md`, `packages/orchestrator/MODULES.md` for the modules a package touches, `documentation/decisions/README.md` and every ADR the package names.
2. **One work package, one change set.** Give each package its own `documentation/work/<slug>/` with requirements, plan and report, as root `AGENTS.md` describes. Do not mix packages in one change set.
3. **ADR packages stop twice.** First write the ADR as `Proposed` under the next free ID (0057 or later; check for collisions right before writing) with the sections `documentation/decisions/README.md` requires. An accepted ADR body is never edited: an amendment is a new ADR, and after acceptance only the older ADR's lifecycle metadata and the index change. Then stop and ask the owner to accept it. No code may rely on a `Proposed` ADR.
4. **Pinned ADRs.** ADRs 0043, 0044, 0045, 0047, 0049, 0050, 0054 and 0055 are pinned by SHA-256 as instruction-transition authorities in `packages/orchestrator/phase-guidance-current.json`. Changing even their lifecycle metadata fails `npm run verify` unless the allow-list in `packages/orchestrator/scripts/phase-resources-build.mjs` records the exact before and after image, keyed by the amending ADR. Add every new ADR to `FIXTURE_PATHS` in `packages/orchestrator/test/release-validation.test.ts`.
5. **Gates stop the stage.** After the last package of a stage, run the gate checks, report the evidence and wait for the owner before starting the next stage.
6. **Checks before calling a package done:** `npm run verify` (typecheck, lint, test, build check) and `npm run format:check`; `npm run release:check` when release, version or instruction-layout files change. Live vendor probes run only with the owner's explicit go-ahead: `npm run compatibility:live -- --confirm-live` (ADR-0011). Today the live suite runs only a read-only review scenario, so WP7, WP8, WP13 and WP14 add their own scenarios.
7. **Instruction text.** `packages/orchestrator/src/phase-resources.ts` is generated: run `npm run build`; `npm run build:check` fails while it is stale. Instruction baselines live in `packages/orchestrator/phase-guidance-current.json` and change only through `packages/orchestrator/scripts/instruction-baseline.mjs` with an authorization that cites an Accepted ADR (ADR-0044, `documentation/engineering-quality.md`). Golden prompt digests sit in `packages/orchestrator/test/prompts.test.ts`. Even a package without a new ADR must cite an existing Accepted ADR as the authority for an instruction change.
8. **Claude environment.** Set new Claude variables at the Claude adapter call sites in `adapters.ts`, not in `subscriptionOnlyEnvironment` (`process.ts`), which also feeds Codex, preflight and project verification commands.
9. **Human actions and `banzai control`.** A new gate or blocked-run action (WP4, WP9, WP10, WP11) needs matching `banzai control` support (`agent-control.ts`, `plugins/banzai/skills/orchestrate/references/control-protocol.md`) and a major control-protocol revision (ADR-0055).
10. **Templates.** `plugins/banzai/AGENTS.md`, `CLAUDE.md` and `PROJECT_MANIFEST.md` are end-user templates, never rules for this repository. WP12 restructures them; WP7 and WP11 also update the passages that describe roles, routing and decision gates.
11. **Language.** UI copy, documentation, ADRs and work reports are in English; talk to the owner in Ukrainian, as root `AGENTS.md` says.
12. **Keep facts current.** Update `PROJECT_MANIFEST.md` (current state only), `documentation/orchestrator.md` and `documentation/getting-started.md` whenever user-visible behaviour changes.
13. **No commits or pushes** without the owner's go-ahead. Git visibility grants no approval, staging, commit or push authority.
14. **Report per package:** what changed and where, tests added, deviations from this brief, and open questions.

## Context

Two developers used banzai 2.7.4 on real tasks. Developer A ran a strict workflow through the CLI in a PHP project inside Docker. Developer B used Claude only: `project-manifest`, then `feature` twice.

Keep what worked; no package may regress it:

- the lite `feature` flow: work.md with numbered requirements, code and tests, typecheck and lint, and checks against a live server (bad config, busy port, shutdown);
- run state and evidence kept under the Git-ignored `.banzai/`, plans as plain Markdown;
- spec-gate staying quiet in repositories that have not adopted banzai.

### The run that could not be saved

1. The planner wrote the mandatory check `phpcs-dry-run` without `--config=.php-cs-fixer.php`. The plan gate shows only file paths, so the plan was approved without anyone seeing the command.
2. Implementation succeeded: 27 min 23 s, 218 turns, 10/10 tasks, 35 files, 59.3M input tokens (98% cached).
3. Verification failed on the first check. The other two, `schema-catalog-check` (required) and `phpcs-touched-src` (supplemental), stayed "not run" because the runner stops after the first failure.
4. The status listed each check's outcome (`phpcs-dry-run (required): failed`, the rest "not run") under one generic block reason: "Task verification is incomplete. Inspect the retained physical evidence and retry the failed check without replaying implementation." It showed no command, exit code, stderr or log path, although `banzai status --json` carries the raw attempt records. The developer suspected Claude and Docker resources (22 GB memory, 6 CPUs).
5. "Retry the failed read-only attempt" re-ran the same command on the same files and failed again.
6. ADR-0049 requires ordinary reapproval for a changed mandatory check, but a run blocked in verification has no direct route back to approval. The only indirect route (edit the approved plan, Retry, then "Rerun planning to correct the approved plan") voids the approval, re-plans and re-implements. The developer cancelled. The code stayed in the working tree, because the runner never resets, but the approval, the completion ledger and the verification and review continuation were gone, along with 2 h 36 min spent waiting for decisions.

### Other friction

- Editing plan.md by hand or with another AI breaks approval: `planRemainderSha256` must be recomputed manually (WP4).
- The gate asks for a decision as soon as the documents exist and does not say the run waits while files are edited (WP4).
- Workflow selection is opaque, with no way to change it (WP11).
- `/plugin` is missing in the VS Code chat; the guide shows no terminal commands; the default user scope puts 9 skill descriptions into every session in every repository (WP5).
- The AGENTS.md template (333 lines) loads into every session; Developer B counted about 670 added lines in an empty repository (WP12).
- Models live in the committed `.banzai/config.json`, so a developer without Codex must edit a shared file (WP6).
- Two vendor subscriptions at about $100–120 a month each (WP7).

## Decisions already made

The owner made these decisions on 30 October 2026. Treat them as settled; the ADRs still need their own acceptance.

1. **Developer value first.** The security and trust track is deferred (see Out of scope). Do not weaken existing protections while working on other packages.
2. **ADR changes are welcome.** The owner is open to a route that corrects a mandatory verification command without re-implementation (amends ADR-0049, WP9) and to the runner recomputing the plan digest after a human edit (amends ADR-0051, WP4). Each ADR still goes Proposed → Accepted before code relies on it.
3. **Codex is no longer the default reviewer.** The default is Claude for all three roles, with the reviewer in a fresh session. Users pick the reviewer model, Codex included, in `banzai init` and `banzai model`. This replaces the principle in `documentation/orchestrator.md` ("Keeping the reviewer on a different vendor than the implementer is the point of the loop"): reviewer independence now rests on a fresh session and reviewer isolation (WP7), and Stage 3 measures what a second vendor adds (WP15).

## Stage 1 (2.8): daily friction

Goal: no run is lost to an unexplained verification failure, plans can be edited safely, and a Claude-only developer can install and configure banzai without touching shared files.

### WP1 · Verification failure details and retry warning

**Problem.** The status already lists each check's outcome (`<id> (required): failed`, `not run`), and `banzai status --json` carries the raw attempt records. The human-readable output still shows no argv, exit code, stderr or log path, and the block reason is one generic sentence, so people guess at the cause. Retry re-runs the same descriptor on unchanged files and fails the same way, with no warning.

**Where.**

- `packages/orchestrator/src/workflow.ts`: the `blockState(state, "Task verification is incomplete. …")` call in `executeTaskChecks`, and the verification runner that records status, failure category and signal.
- `packages/orchestrator/src/verification-ui.ts`: `taskVerificationStatusLines` (extend it).
- `packages/orchestrator/src/interactive.ts`: blocked-run actions ("Retry the failed read-only attempt").
- `packages/orchestrator/src/process.ts`: how timeouts and signals are reported.
- `plugins/banzai/lib/task-verification-store.mjs`: attempt records in `.banzai/runs/<run>/verification/attempts/*.finish.json`, logs in `.banzai/runs/<run>/verification/logs/<attempt-id>.stdout.log` and `.stderr.log`.

**Change.**

- Extend `taskVerificationStatusLines` and the block reason: for each failed, timed-out, interrupted or unavailable check, show argv and cwd, exit code or signal, failure category, duration, the last 20 lines of redacted stderr (stdout when stderr is empty), and repository-relative log paths.
- Key every label on status, failure category and signal together. A timeout is killed and usually recorded as `interrupted` with category `timeout`; a Ctrl-C or out-of-memory kill is `interrupted` with `command_exit`; a non-zero exit is `failed` with `command_exit`; a signal yields a synthetic exit code 1; a process-start failure carries the placeholder stderr "Process could not be started."
- `banzai status --json` already prints the raw `taskVerification` state. Decide whether a stable, documented projection is worth adding, and do not break existing consumers.
- Retry label: compare the failed attempt's descriptor and observed input digest with the current ones when the blocked-run menu is shown, not on every `status()` call (the input capture can read up to 128 MiB). For an unchanged command exit, label the action "Retry anyway (same command, same files; expected to fail again)". After WP9 lands, offer "Correct a verification command" next to it.

**Done when.** A fixture run with a failing required check shows every field in the blocked summary and `banzai status`; labels are right for each combination of status, category and signal; the retry label changes only for an unchanged command exit; output stays redacted and terminal-escaped.

**ADR.** None: presentation over existing ADR-0015 and ADR-0049 records. **Size.** About 2 days.

### WP2 · Run every required check in one pass

**Problem.** `executeTaskVerification` leaves its loop after the first attempt that did not complete (`if (terminal.status !== "completed") break;`), so later checks show "not run" and each fix costs another round. This is the decided behaviour today: ADR-0045 says "Ordinary runner verification still stops on its first failure"; only `verify check` attempts all commands.

**Where.** `plugins/banzai/lib/task-verification-store.mjs` (`executeTaskVerification`, `taskVerificationApplicability`, the `retryOf` handling); `packages/orchestrator/src/retry-eligibility.ts` and the retry path in `workflow.ts`; `plugins/banzai/lib/verification-helper.mjs`, which shares this code; `interactive.ts` (retry labels); `packages/orchestrator/test/task-verification.test.ts`.

**Change.**

- After a command-level failure (non-zero exit, timeout, unavailable executable), continue with the remaining checks in order. Keep stopping on interruption, ownership or setup failures and changed inputs: those paths stay fail-closed.
- Make retry handle several failed checks in one round. Today retry eligibility looks only at the latest attempt, `executeTaskVerification` accepts one `retryOf`, and any other failed attempt in the same round fails with "Task verification retains an unresolved attempt". Retry every failed check of the round in one action, and keep the menu label from falling back to "Retry start checks".
- Define the case of a failing check that writes files. The input snapshot is taken once per round and compared before every launch, so the next check would fail closed: report which check changed which files, and stop.
- The aggregate outcome stays failed while any required check fails.

**Done when.** With three required checks and the first failing, all three have attempts and dispositions; with two failed checks, one retry action reruns both; existing fail-closed tests pass unchanged.

**ADR.** New ADR amending ADR-0045's rule for ordinary runner verification. **Size.** 2–3 days plus the ADR.

### WP3 · Verification commands at the plan gate, taken from documented commands

**Problem.** The plan gate prints artifact paths and human prerequisites only. Mandatory checks sit in the `banzai-verification-obligations/v2` JSON block of plan.md, so a missing config flag goes unnoticed. The planner already receives "Inert project discovery" with `npm run` and `composer run-script` suggestions, but no rule asks an obligation to use the project's documented command with its config flags. ADR-0049 already requires the checks to be readable in plan review.

**Where.** `interactive.ts` (the `needs_plan_approval` branch); `verification-ui.ts` (`verificationCommandLines` formats profile commands; add a sibling for v2 descriptors); `banzai status`. Runner planning receives the policies, not SKILL.md: the canonical obligations text is "Task verification obligations" in `plugins/banzai/policies/plan-task-completion.md`, plus the planning instruction in `prompts.ts`. Discovery comes from `discoverTaskVerification` in `plugins/banzai/lib/task-verification.mjs` and is passed to the planner in `workflow.ts`. Update `plugins/banzai/skills/development-plan/SKILL.md` for the standalone skill path.

**Change.**

- Before the plan decision, print "Verification that gates completion": one line per check with id, required or supplemental, argv, cwd, timeout, and the materialization task when the tooling does not exist yet. Show the same list in `banzai status`.
- In the policy, the planning instruction and the skill: build each obligation from the project's documented command (manifest, `composer.json` or `package.json` scripts, Makefile, CI) with its config flags; prefer the discovered script entry point (`composer run-script <name>`, `npm run <name>`) when one exists; cite it in `sources`. Build on the existing discovery rather than duplicating it.

**Done when.** The plan gate and `banzai status` list the obligations of a fixture plan; the instruction change goes through an ADR-0044 transition and the golden prompt tests; WP15 gets an eval case for this rule.

**ADR.** None new; cite ADR-0049 as the authority for the instruction change. **Size.** About 1 day.

### WP4 · Re-check human edits at the plan gate

**Problem.** `planRemainderSha256` covers every byte of plan.md outside the inventory block. After any manual or AI-assisted edit, approval fails with `TASK_VERIFICATION_DIGEST_MISMATCH`; the error shows the observed digest, and the practical way out is to paste it into the JSON block by hand. On schema-10 runs the gate also offers Request rework, but then the planner re-authors the plan and its digest at the cost of a model round, and the human edits may not survive. The gate never says that the run waits and that the files may be edited.

**Where.** `interactive.ts` (plan gate choices and copy); `workflow.ts` (`approvePlan`); `plugins/banzai/lib/task-verification.mjs` (`parseTaskVerificationObligations`); `packages/orchestrator/src/workflow/completion/plan-tasks.ts` (`establishPlanRemainderDigest`); `cli.ts` (`banzai approve plan`); `agent-control.ts` and the control protocol for the new action; ADR-0051.

**Change.**

- Add the gate choice "Re-check my edits", a CLI equivalent on `banzai approve plan`, and a `banzai control` action with the matched control revision.
- The runner re-reads description, ADRs and plan; validates the plan structure and the obligations inventory; recomputes `planRemainderSha256` and rewrites only that field; shows a short diff against the planner's version (changed sections, changed obligations); then asks for the decision again.
- The approval record marks the human edit and keeps the planner-authored digest for audit.
- Gate copy, with full paths: "The run is waiting. Edit these files in any editor, then choose Re-check my edits. Exit and decide later keeps the run."

**Done when.** A prose edit to plan.md is re-checked and approved without manual hashing; an edit that breaks the inventory or the task headings is refused with a precise message; a model-authored digest mismatch on a fresh planner result still follows ADR-0051's existing route; tests cover all three.

**ADR.** New ADR amending ADR-0051: under human authority at the plan gate, the runner recomputes the remainder digest. Proposed, then owner acceptance, then code. **Size.** 2–4 days plus the ADR.

### WP5 · Install guide, plugin scope, doctor hint

**Problem.** `documentation/getting-started.md` shows only in-session `/plugin` commands, which the VS Code chat does not offer. The default user scope loads 9 model-invocable skill descriptions (about 2,000 characters) into every session in every repository; only a phrase in each description ("Auto-select only in a Banzai-adopted repository") keeps them from triggering elsewhere.

**Where.** `documentation/getting-started.md` (Claude Code plugin section), `README.md`, `packages/orchestrator/src/doctor.ts` and the Claude settings reader in `claude-permissions.ts`.

**Change.**

- Add terminal commands for Claude Code:

```bash
claude plugin marketplace add Parabolic-Technologies/banzai --scope local
claude plugin install banzai@banzai-plugins --scope local
```

- Recommend `--scope local` (`.claude/settings.local.json`: this repository, this developer) for a first try and `--scope project` (`.claude/settings.json`, shared through Git) for a team. User scope stays possible but is no longer the suggested default.

Doctor stays offline (ADR-0008): read the settings files the way it already reads Claude permission settings, and never run `claude plugin list`. A new doctor check changes the `banzai-doctor/v5` JSON contract, so version it as `documentation/orchestrator.md` describes.
- Investigate, without shipping, whether skill `paths:` frontmatter can limit automatic loading to adopted repositories. The docs say it limits automatic loading; they do not say whether the description stays in context. Record the findings for WP15.

**Done when.** A new user installs from a terminal or VS Code by following the guide alone; doctor prints the hint for user scope and nothing for local or project scope; existing documentation checks pass.

**ADR.** None; stay within ADR-0008. **Size.** 1–2 days.

### WP6 · Local model override

**Problem.** `.banzai/config.json` is committed: `init` Git-ignores only run state (`runs/`, `verification/`, `execution-locks/`, `runner.lock`, `active-run.json`). `banzai model` writes that file and `loadConfig` reads only it, so a developer without Codex has to edit a shared file.

**Where.** `packages/orchestrator/src/config.ts` (`CONFIG_FILE`, `loadConfig`, `initializeConfig`, model update helpers); `cli.ts` (`init`, `model`) and the picker in `model-selection.ts` (`selectModelSettings`); `plugins/banzai/lib/execution-ownership.mjs` (`ensureExecutionIgnores`); `doctor.ts`, which has its own config reader; `banzai status`.

**Change.**

- Add a Git-ignored `.banzai/config.local.json`, merged over the committed file for `models` only (executable, model and effort per role). Verification policy, context limits and every other key stay team-owned; the loader refuses other keys in the local file.
- `banzai model --local` writes the local file; the interactive picker asks where to save when the committed file is tracked by Git.
- `init` adds the local file to `.gitignore`.
- `doctor` and `status` show the effective model per role and where it comes from. Doctor's own config reader and its `banzai-doctor/v5` JSON need the same change, versioned.
- Guard the run: `banzai model` refuses changes during an active run, but phases call `loadConfig` fresh, so a hand edit of the local file mid-run would switch models silently. Snapshot the effective models at run start, or refuse to continue when the local file changed.

**Done when.** With a committed Codex reviewer and a local Claude reviewer, phases run with the local choice and `git status` stays clean; refused keys and the active-run guard are tested; doctor shows the source of each value.

**ADR.** Check eligibility in `documentation/decisions/README.md`. Config precedence is a cross-cutting contract, so a short ADR is likely. **Size.** 1–2 days.

### WP7 · Claude as the default reviewer, with reviewer isolation

**Problem.** `DEFAULT_CONFIG` reviews with Codex `gpt-6.1-sol`, so a Claude-only developer must change the shared config, and the docs present a second vendor as the point of the loop. With Claude reviewing by default, three leaks become review-quality issues:

- auto memory loads the repository's shared `MEMORY.md` (up to 25 KB) into every Claude phase, so the "fresh" reviewer reads what the builder saved;
- the `Skill` tool lets the reviewer run built-in commands, including Claude Code's own review. ADR-0042 §7 and ADR-0037 deliberately kept `Skill` in phase tool inventories, so removing it is a decision, not a cleanup;
- a request flagged by the safety classifier is re-run on another model, and the session stays on it.

**Where.** `config.ts` (`DEFAULT_CONFIG.models.reviewer`, `DEFAULT_TASK_CONFIG`); the picker in `model-selection.ts` (`selectModelSettings`), called from `cli.ts`, and the catalog in `models.ts`; the Claude call sites and `buildClaude*Arguments` in `adapters.ts` (review and planning review share `buildClaudeArguments` with `Read`, `Glob`, `Grep`, `Skill`; builders also receive `Skill`; selection already excludes it); `claude-permissions.ts`; `live-compatibility.ts` (expects `Skill` for the reviewer); `PROJECT_MANIFEST.md` (default models, minimum client versions); `documentation/getting-started.md` (prerequisites); `documentation/orchestrator.md` (model configuration); `README.md`; the Roles section of the `plugins/banzai/AGENTS.md` template.

**Change.**

- Default reviewer: Claude `claude-opus-5-5` in a fresh session, with the planning effort unless the owner decides otherwise. `init` and `banzai model` keep offering Codex.
- Set `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for Claude phases (the reviewer at minimum) and `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` for the reviewer, at the Claude call sites.
- Remove `Skill` from the `--tools` of review and planning review, and update the live-compatibility expectations. The ADR decides whether builders keep it.
- Rewrite the principle in orchestrator.md: reviewer independence comes from a fresh session with no builder transcript and no shared memory; a different vendor is an option, not a requirement.
- Update prerequisites (Codex CLI only when a role uses it) and the template's Roles text.
- Add a live-compatibility scenario for a Claude reviewer.

**Done when.** A fresh `banzai init` with only Claude Code installed proposes Claude for all roles and passes doctor; argv and environment tests assert the variables and the tool list per phase; existing configs with a Codex reviewer keep working unchanged; docs, manifest and template are updated; the owner-authorized live scenario confirms the reviewer's tool list without `Skill`.

**ADR.** New ADR recording the default-reviewer decision and the isolation requirements. It amends ADR-0042 §7 and ADR-0037, which kept `Skill` in the inventories, and replaces the documented vendor principle. **Size.** 2–3 days plus the ADR.

### WP8 · Stable Claude phases: minimum 2.1.290, no background tasks, prompt over stdin

**Problem.**

- Before Claude Code 2.1.290, a headless `--json-schema` run could exit non-zero with `is_error: true` on a successful result when the connection dropped after the structured output arrived, so a phase that succeeded counted as failed. The banzai minimum is 2.1.218 (2.1.280 for the default models).
- Since 2.1.292, a one-shot `claude -p` run waits for background commands that the main conversation started, then gives Claude one more turn. banzai expects one terminal result per phase; a second one would be refused as `TERMINAL_RESULT_CONFLICT` (confirm with a live probe).
- The phase prompt travels as one argv argument. Linux caps a single argument at 128 KiB; the earlier analysis measured 34–53 KiB of embedded phase instructions and up to 64 KiB for a `banzai control` request.

**Where.** `adapters.ts` (`MINIMUM_CLAUDE_VERSION = "2.1.218"`, the startup preflight `requireVersion` and its `CLI_TOO_OLD` error, `buildClaude*Arguments`, the Claude call sites); `process.ts` (the spawn uses `stdio: ["ignore", "pipe", "pipe"]`); `live-compatibility.ts`; `PROJECT_MANIFEST.md`; `documentation/getting-started.md`.

**Change.**

- Set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` and `BASH_MAX_TIMEOUT_MS` (with `BASH_DEFAULT_TIMEOUT_MS` if needed) at the Claude call sites, so a foreground command can run as long as the phase allows. Defaults are 2 and 10 minutes.

**Done when.** Tests assert the environment and that no argv element carries the prompt; a prompt larger than 128 KiB starts a phase in a fixture; a new owner-authorized live scenario confirms one terminal result after a long-running command, on 2.1.290 and on the current client.

**ADR.** Probably none. Check whether ADR-0020 (scoped Claude subprocess environment) needs an amendment for the new variables. **Size.** About 2 days.

## Stage 2 (2.9): no lost runs

Goal: a wrong verification command costs a correction and one more verification round, not a cancelled run; workflow choice is explained and changeable; sessions carry less always-on text.

### WP9 · Correct a verification command without re-implementation

**Problem.** ADR-0049 (section 4) and ADR-0043 require ordinary reapproval for a changed mandatory descriptor, but a run blocked in task verification has no direct route back to approval. The only indirect one (edit the approved plan, Retry, then "Rerun planning to correct the approved plan" after `approval_invalid`) voids the approval and the completion checkpoint, reruns the planner, which may rewrite the human edit, and re-implements. `validateApproval` itself tells users to cancel and approve a revised plan in a new run. ADR-0025 removed the same kind of trap for completion evidence after fixes.

**Where.** `interactive.ts` (blocked-run actions); `cli.ts` (a new subcommand) and `agent-control.ts` with the control protocol; `workflow.ts` (verification state, `approvePlan`, `retryIntoPlanning`, the round id derivation); `workflow/preflight/approval.ts` (`validateApproval`); `workflow/completion/revalidation.ts` (completion bound to its approval); `plugins/banzai/lib/task-verification.mjs` and `task-verification-store.mjs` (inventory parsing, rounds, attempts); ADR-0049, ADR-0047, ADR-0043, ADR-0025.

**Change.** A new action, "Correct a verification command", for runs blocked in task verification:

1. The human edits the descriptor of one or more required checks (argv, cwd, timeout), or asks the planner for a proposal with the failure output attached (a read-only, planning-scoped call).
2. The runner validates the new descriptors with the planning rules, writes the amended inventory into plan.md, recomputes `planRemainderSha256` and shows the obligation diff.
3. The human approves the amendment. A new approval record links to the original approval and names the changed checks.
4. Verification starts a new round with the amended descriptors; derive a new round id, since today it is reused per source attempt. Implementation is not replayed, and earlier attempts stay in evidence.

Not allowed on this route: removing a required check, making it supplemental, or changing task scope and obligations beyond the check descriptors. Those still need full re-planning. Published completion is bound to its approval (`revalidation.ts`: "Published completion was authorized under a different approval", ADR-0047), so the design must carry completion over to the amendment approval without re-implementation, for example by linking the two approvals and revalidating completion against the amended one.

**Done when.** The phpcs fixture is fixed end to end without re-implementation; the audit trail shows both approvals and every attempt; forbidden amendments are refused with a clear message; interruption and resume in the middle of an amendment are tested; the action also works through `banzai control`.

**ADR.** New ADR amending ADR-0049 §1 (a planner call that proposes a correction), §2 (the human edits argv) and §4 (the reapproval route), and affecting ADR-0047 (completion bound to approval); cite ADR-0043 and the ADR-0025 precedent. **Size.** 1–2 weeks plus the ADR.

### WP10 · Baseline check run before implementation

**Problem.** A wrong command surfaces only after implementation: 27 minutes into the phpcs run.

**Where.** `workflow.ts` (between plan approval and the first implementation attempt); `task-verification-store.mjs` (a separate attempt kind for baseline runs); `config.ts` (a setting); `interactive.ts`.

**Change.** After plan approval and before implementation, run the required checks that need no future tooling (`materialization: null`) on the untouched tree, with their own timeouts. Results are advisory: never evidence, never counted toward obligations, stored apart from verification rounds. When a check fails, show the WP1 details and offer: continue, correct the command through the WP9 route, or cancel; expose the choice through `banzai control`. Proposed default: on for short checks (lint, static analysis), opt-in for long test suites; the ADR settles the default.

**ADR.** New ADR for the new step and its evidence boundary (relates to ADR-0049 and ADR-0043). **Size.** 3–5 days plus the ADR.

## Out of scope

The owner deferred the security and trust track. Do not implement these items in 2.8–2.9 unless the owner reopens them, and do not weaken the protections that exist today.

- Without `--bare`, `claude -p` runs project hooks and `env` from the repository's settings and connects `.mcp.json` servers even in a folder nobody trusted; banzai also passes the repository's `.mcp.json` Serena entry to phases and to `banzai setup`. - An ask hook for the `orchestrate` gate commands (`banzai approve`, `banzai triage`, `banzai cancel`, `banzai control`): in auto mode the classifier, not a person, approves them.
