# Banzai 2.6.0

Release following [2.5.0](2.5.0.md), with runner-owned completion projection
under [ADR-0047](../decisions/0047-runner-owned-completion-projection.md) and
the completion markup and viewer enrichment boundary under
[ADR-0048](../decisions/0048-completion-markup-and-viewer-enrichment-boundary.md).

## Changes since 2.5.0

- Strict implementation and fix attempts return structured task claims and
  report narrative only. The runner validates those claims and then renders and
  publishes the implementation report's **Plan Task Completion** section itself,
  so no model writes, escapes or repairs that table and a valid narrative-only
  report reaches verification without a formatting-only model call.
- The published region is a bounded, delimited section. Every byte outside it is
  preserved, exactly one existing legacy or generated section is replaced, and
  ambiguous ownership fails before any overwrite. Cell payloads are encoded so
  model characters cannot create Markdown or HTML syntax; viewer enrichment of
  decoded plain text remains outside that guarantee.
- Completion publication is durable and recoverable. The runner retains the
  terminal input observation, an immutable capture, the rendered candidate and a
  publication receipt, then applies the result once. An interruption either
  reconciles the same proven bytes without another model call or blocks with a
  closed refusal code: transient storage failure resumes, drift requires
  restoring the exact recorded input, proven output and authority before resume,
  and unusable proof exposes cancel.
- Publication authority covers the base commit, approval, plan tasks, attempt
  scope, work binding and the implementer configuration. Report or workspace
  bytes written after the model returned are never adopted as the recorded
  input.
- Accepted-finding fixes refresh completion evidence through the returned ledger
  only. A refreshed ledger is republished with the fix as its author, a fix that
  returns no ledger republishes the retained canonical ledger under a new
  publisher, and an edit inside the published region carries no authority.
- Rejected claims and structurally ambiguous report input fail the attempt and
  offer one linked evidence-repair successor that preserves the rejected source.
- Downstream boundaries revalidate a published completion strictly read-only
  against its receipt, final report hashes, ledger author and published region.
  Independent review freezes those identities instead of re-reading mutable
  report text.
- Agent control publishes contract `5.0.0` with `banzai-agent-capabilities/v5`
  and `banzai-agent-status/v4`. Capabilities declare the publication protocol,
  its stages, the closed refusal codes and the pending attempt status; status
  adds the bounded publication state so a supervisor can route resume or cancel
  from machine evidence.

## Compatibility

- Supervisors negotiate on the exact capability declaration, not the package
  version. A supervisor pinned to capabilities v4, status v3 or control `4.0.0`
  must accept the current identities before driving a run.
- Historical evidence keeps its original meaning and bytes. Model-authored
  `banzai-plan-task-completion/v1` projections, completion summary 1, terminal
  checkpoint 1, model attempt records 1 and 2 and run state 1 through 6 retain
  their readers, and nothing is migrated in place.
- Run state advances to schema 7 only when a new strict implementation or fix
  attempt is created. New runs still start at schema 4 or 6 according to their
  configuration, and inspection never upgrades a run.
- Standalone work is unchanged: authors keep writing the
  `banzai-plan-task-completion/v1` table in their own reports, and readers
  recognize both that projection and the runner-published region without
  treating either as independent evidence.
- The plugin and orchestrator share version **2.6.0** and remain separately
  installable and deliverable. See the
  [getting-started guide](../getting-started.md) for supported hosts, runtimes,
  and client setup.
